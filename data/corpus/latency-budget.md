# 延迟预算的分配方法

线上推理服务的延迟由四段组成：排队、预填充（prefill）、解码（decode）和网络回传。

在我们 2026 年 Q1 的采样中，一个 P95 为 2.8 秒的接口，四段占比大致是：排队 8%、预填充 22%、解码 61%、回传 9%。解码占大头，是因为输出长度不可控——同一个 prompt 在不同请求里输出长度可能相差 5 倍。

预填充阶段与输入长度近似线性。输入从 800 token 涨到 3200 token 时，预填充耗时从 140 毫秒涨到 520 毫秒，基本是 4 倍输入对应 3.7 倍耗时。

解码阶段的时间由输出 token 数决定，单 token 的生成速度在 A100 上约为每 token 28 毫秒，在 H100 上约为每 token 15 毫秒。这个比值在 batch 变大时会劣化：batch size 从 1 升到 16，单 token 耗时增加到 1.8 倍。

因此延迟优化的优先级应该是：先控制输出长度，再优化排队，最后才考虑换硬件。很多团队一上来就换卡，但输出长度不设上限时，换卡只能带来 40% 左右的改善。

需要注意，平均值会掩盖问题。我们统计过，平均延迟 1.1 秒的服务，P99 可以达到 6.4 秒，因为少量请求触发了长输出和重试。
