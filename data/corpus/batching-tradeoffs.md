# 批处理的吞吐与延迟权衡

连续批处理（continuous batching）是提升吞吐的主要手段，但它和延迟目标直接冲突。

在 8 卡 A100 上，batch size 为 1 时，单请求解码速度是每 token 28 毫秒，吞吐 36 token/s。batch size 提到 32 时，单请求速度劣化到每 token 74 毫秒，但总吞吐升到 430 token/s——吞吐提升 12 倍，单请求延迟劣化 2.6 倍。

这意味着批处理本质上是把延迟卖给了吞吐。如果一个服务同时要求低延迟和高吞吐，唯一可行的做法是排队上限加超时降级，而不是把 batch size 调到一个折中值。

我们踩过的坑是动态批处理窗口设得太宽。当窗口设为 50 毫秒时，P50 延迟只增加了 30 毫秒，但 P99 增加了 640 毫秒，因为窗口内偶发的长请求会把整个批次拖住。

更稳的做法是按 token 数而不是请求数限批。同样是 32 个请求，如果其中有 3 个请求的输入超过 8000 token，GPU 显存占用会接近上限，触发降级。我们改成"批次总 token 不超过 24000"之后，显存相关的事故从每周 2 次降到零。

流式输出可以掩盖一部分批处理延迟：用户在看到首 token 后对后续延迟的容忍度明显提高。实测首 token 在 800 毫秒内返回时，用户感知到的"快"与总时长 4 秒的请求差别不大。
