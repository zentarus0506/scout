# Scout

> 一个会核查自己引用的研究 agent。

深度研究类产品的核心风险不是「答不出来」，而是**答得很像样，但引用是编的**。用户看到 `[cost-structure#0]` 这样的角标，会默认这句话有出处，于是不再核对——这比没有引用更危险。

Scout 的每条结论都必须绑定到一个具体段落，并在写进报告之前经过算法核查。

## 五种核查结果

算法不判断语义对错，只回答「证据够不够」。所以结果不是二元的是非，而是五种状态——**把「找不到证据」和「证据反驳」混为一谈，是核查工具最常见的失真**：

| 结果 | 含义 | 触发条件 |
|---|---|---|
| **已证实** | 引文支持该结论 | 词项覆盖 ≥ 55%，且无下列异常 |
| **证据较弱** | 部分支持，改写幅度较大 | 覆盖 30%–55%，无异常 |
| **未找到足够证据** | 核查器无法判断（≠ 结论错误） | 覆盖 < 30%，无异常 |
| **与引文矛盾** | 引文明确反驳该结论 | 数字不存在 / 否定反转 / 过度概括 |
| **引文不存在** | 引用指向不存在的段落 | ref 无法解析 |

能自动发现的四类硬错误：

| 失败类型 | 例子 | 检测方式 |
|---|---|---|
| **数字幻觉** | 原文「200 token」，结论「607 token」 | 结论中的每个数字必须在引文中出现 |
| **否定反转** | 原文「最终没有启用」，结论「启用了」 | 结论有否定而引文没有 |
| **过度概括** | 原文「在我们的测试中」，结论「所有场景都成立」 | 结论有绝对化表述而引文没有 |
| **坏指针** | 引用了 `ghost-doc#7` | 与「矛盾」分开报告 |

这些检查都不调用模型。这是刻意的：**让写结论的模型给自己的结论打分，等于没有核查。**

### 一次成本优化，完整走完「测量 → 决策 → 验证」

用 Lens 给 Scout 加埋点之后，第一眼就看到了问题：一次研究 `$0.001668`，其中**结论抽取一项占 71%**（`$0.001185`），因为它把全部 8 段检索结果塞进了一个 prompt。

于是把 `claim_context` 做成参数，测了三种配置（同一问题，成本数据从 trace 读，不是自己算的）：

| 配置 | tokens | 成本 | 结论数 | 核查通过率 |
|---|---|---|---|---|
| 8 段全传（原） | 2524 | $0.001664 | 6 | 83% |
| **top-4（现默认）** | 1698 | **$0.001163** | 6 | **100%** |
| top-4 + 每段截断 600 字 | 1546 | $0.001045 | **3** | 100% |

**top-4 省 30% 成本，核查通过率反而从 83% 升到 100%，结论数不变。**

为什么质量会上升？合理的解释是上下文稀释：8 段里有 4 段与问题关系较弱，模型在它们上面容易张冠李戴；砍掉之后，每条结论更容易落在真正相关的段落上。

**没有采用更省的截断方案**，因为它的代价是结论数从 6 掉到 3。通过率 100% 但只说了三件事，这是「少说少错」，不是质量提升。**覆盖率必须和准确率一起看**。

两点诚实说明：

- **n = 1**。每个配置只跑了一次，通过率的 83% → 100% 完全可能是单次波动。要下结论应该重复 5-10 次（Tiny 那个项目专门论证过这件事）。
- **延迟数据不可信**。top-4 那次测出 50.6 秒，比上下文更多的 baseline 还慢一倍，明显是 API 波动或重试。成本数据可复现，延迟数据不可。

复现：`python examples/bench_cost.py`（需要可用 key）

## 快速开始

```bash
uv venv && uv pip install -e .
.venv/bin/python -m scout.cli demo        # 对照演示：正常 vs 故意篡改
.venv/bin/python -m scout.cli ask "为什么只优化平均延迟是不够的？" --offline
```

`demo` 会跑两遍同一个问题：第一遍结论逐字取自原文（应当全过），第二遍故意改数字、加绝对化表述，让你看核查器怎么把它们拎出来。

不配置任何 key 也能完整运行——所有检索、切分、核查都是算法。

配置真实模型后，问题拆解和报告组织会交给 LLM：

```bash
# .env
SCOUT_PROVIDER=siliconflow
SCOUT_MODEL=deepseek-ai/DeepSeek-V3.2
SCOUT_TRUST_ENV=0
```

### 接入 Lens 追踪

```bash
pip install -e ../lens          # 可选依赖
.venv/bin/python -m scout.cli ask "..." --trace
```

一次研究会记录成一条 run，三次模型调用各自成为一个 span，带 token 数和成本。Scout 不 import Lens 也能正常工作——`tracer` 只要求 `span()` 和 `record_llm()` 两个方法，任何兼容的对象都能接上。

## 架构

```
问题
 └─ decompose    拆成 2-4 个子问题（LLM，失败则按分句规则拆）
     └─ retrieve  BM25 检索，去重后取 top-N 段落
         └─ extract  从段落中抽取带 ref 的结论（LLM，失败则逐字摘句）
             └─ verify   算法核查每条结论（始终执行，不依赖模型）
                 └─ synthesize  组织成报告（LLM，失败则模板）
```

关键设计：**模型是增强项，不是必需项**。检索、切分、核查全部是算法，所以这个工具在没有 key 的机器上、在 CI 里、在断网时都能跑，能跑出确定的结果，也能被测试覆盖。

## 语料

`data/corpus/` 里有 8 篇技术备忘录，主题是 LLM 服务的延迟、成本、缓存、路由、批处理、可观测性和评测方法。它们包含具体数字和互相有张力的结论（比如「语义缓存能提高命中率」但「误命中率 7.3%，最终没上生产」），用来测试 agent 是否会断章取义。

选本地语料而不是搜索 API 的理由很实际：**研究 agent 只有证据可复现才值得信任**。同一个问题每次召回同样的段落，引用核查才能写成断言。

## 设计决策

**BM25 而不是向量检索。** 八篇文档的规模下，稠密检索的复杂度换不来收益，而 BM25 的失败模式是可见的——你能直接看到是哪个词命中了。规模上来之后再换，接口不变。

**中文用字符二元组分词。** 不需要词典，对检索足够；损失在于无法区分同义词，但在这个语料规模上不明显。

**核查只做单向否定检测。** 结论通常引自原文的一段，所以「引文有否定而结论没有」是正常的（结论只是没摘到那句）；「结论有否定而引文没有」才可疑。双向检测会把大量正确结论误判。

**数字检查优先级最高。** 即使文字重合度 98%，只要有一个数字在引文里不存在，就直接判为不支持。模型编造数字的频率远高于编造实体，这条规则性价比最高。

**`Scout.offline()` 是独立构造器。** 传 `llm=None` 意味着「自动探测凭证」，这对命令行是对的，对测试是灾难——在有 key 的机器上，每个测试都会真的发起计费调用。

## 已知限制

- **核查基于词项与规则，不理解语义。** 同义改写（「降低开销」vs「减少成本」）会拉低重合度。现在的处理是把它归到「未找到足够证据」而不是「矛盾」——至少不再冤枉正确结论，但它依然无法被自动证实。真实生产应该叠加一个 NLI 模型做蕴含判断。
- **只检查结论与引文的关系，不检查引文之间是否矛盾。** 语料里 `caching-strategies` 和 `model-routing` 对缓存的结论不同，agent 不会主动指出冲突。
- **语料是内置的。** 接入真实检索需要替换 `Corpus`，但 `get(ref)` 的契约要保留，否则核查无从下手。
- **报告长度受限。** 默认最多 6 条结论，避免上下文过长；这个数字是拍出来的，没有调优。
